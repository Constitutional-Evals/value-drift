## Selection-rule clarification resolved before results

The earlier draft called substantive-edit count primary but subsequently stated failure/simplicity preferences without explicitly restricting them to count ties. The lead clarified the design before diagnostic results: **maximize substantive-endorsed-edit count first; among equal counts prefer fewer technical failures; among remaining ties prefer O, then A, then B.** The 2/3 threshold labels stronger support while 1/3 remains weak exploratory evidence. This resolves the ambiguity without adding samples or conditioning the rule on observed outcomes.

The broader conditioned-study framing is otherwise explicit and appropriate. Seeds 30301–30303 are fixed before outcome inspection; the actual launch uses fresh seed30401. There is no seed-mining rule or authorization to retry an unchanged actual launch within the same trajectory. Selecting a procedure for its observed propensity to yield substantive endorsed edits is disclosed as exploratory, and diagnostic editing rates are not unbiased population estimates. Public summaries and independent semantic diff assessment, rather than hidden reasoning length, determine edit classification. Preserve all nine scheduled results and reviewer disagreements.

## Diagnostic runner audit

Subsequently inspected `scripts/review_diagnostics.py` and `tests/test_diagnostics.py`. The main integration checks above pass:

- Each scheduled trial constructs a new inference session for the same base M0. The explicit seed is placed in its review config and forwarded into `VLLMSession`; a fresh worker resets its request counter. Within a multi-turn review, subsequent calls increment from that seed normally.
- C0 and recipe are loaded from saved literal snapshots. Each trial gets its own editable workspace and one fresh initial conversation. Edited text from one diagnostic never becomes the next trial's input. Both condition instructions and wrapper are rendered from snapshot paths. Shared tool instructions are snapshotted and checked before each new trial.
- The plan, base config, selection rule, all condition files, wrapper, C0, recipe and tool schema are recorded before model startup. Resume compares literal bytes and rejects changes. All scheduled trials are attempted regardless of previous unchanged or edited outcomes; no training/evaluation stage is called.
- A saved result is retained without another inference call. An interrupted trial with artifacts is recorded as failure unless a finalized review can be recovered; it is never replayed. A completed schedule means all attempts were recorded, not that every review succeeded.

Verification: runner, inference-factory and vLLM tests passed **17 tests plus two subtests**. A separate CPU fixture executed the actual nine-trial configuration with mock inference: all nine contexts contained the complete fixed C0 and truthful diagnostic disclosure, all scheduled seeds matched, all nine workspaces were distinct, and resume added zero inference calls. No GPU was initialized.

One concrete edge defect was found and sent to the implementation agent: if session cleanup raises after `execute_review` has saved a valid final submission, the outer exception handler labels the trial only as `DIAGNOSTIC_REVIEW_FAILURE`. A CPU reproduction produced three such failure results while all three saved reviews were `SELF_DECLARED_CONVERGENCE`. Preserve the finalized unchanged/edited observation and record a separate cleanup/runtime error, with no replay. A regression should verify both the outcome and error remain visible across resume. This finding concerns faithful result reporting; it does not justify resampling or discarding the trial.

The lead also clarified that the new remote deadline is a deliberate renewable 72-hour orphan-resource lease, unrelated to dollar spend. The old pod and its guard were terminated; no previous $200-derived cutoff was carried forward.

## Shared stage-2 recipe verified before sampling

The diagnostic now snapshots `configs/stage2-base.json` and its `prompts/variants/training_recipe_v2.md`, rather than the old full-001 base/recipe. Independently compared the new description to `generation.py`, `train.py` and backend stage routing. It accurately describes 1,500 fixed preference prompts; the fixed 27B teacher and neutral student; cached exact pre-update reference probabilities; one DPO epoch with preferred-response likelihood term; post-DPO generation of 512 reflections and 64 four-turn interactions; and direct full-parameter SFT with weights continuing across stages. The interaction SFT retains one perspective's assistant turns and the partner's intervening reply, omitting the final partner turn and the constitution-bearing generation system prompt. Training uses warmup to 1e-5 followed by a constant rate, with optimizer reset at each stage. The public recipe no longer invokes an active budget constraint.

The new 0.5 retention floors are inclusive and independently applied: at least **750 preference pairs, 256 reflections and 32 complete interaction transcripts** must remain. Empty/truncated outputs and identical preference pairs are excluded; one unusable interaction turn excludes its entire transcript, including when that turn would not itself be an SFT target. Retained data and explicit exclusion/quality reports are saved before a below-floor exception stops the stage. The fraction is measured against the requested component count, not the already retained subset. This is a disclosed data-quality threshold, not permission to train on unfinished targets. DPO2560/SFT3072 still reject encoded target truncation before optimization.

Reflection generation now uses 1,536 tokens; the explicit dialogue override uses 768 per turn. These match the code's separate option paths. The earlier measured reflection prompt maximum plus 1,536 fits SFT3072, while three retained dialogue turns at 768 plus the short prompt also fit; actual length audits remain authoritative. The larger evaluation allowance (8,192 output tokens) and judge input allowance (16,384) are separately versioned pre-trajectory choices, not changes to diagnostic review decoding. A direct comparison found only the default review seed differs from full-001; the nine diagnostic seeds override it as planned. The new evaluation baseline must be generated under these new settings rather than treated as interchangeable with the old 2,048-token baseline.

Rendered O/A/B contexts all contain byte-identical C0, the complete new recipe, and honest no-training diagnostic disclosure; counts are now 1,993/2,086/2,301 words. The added shared recipe is another disclosed difference from full-001, common to all three diagnostic conditions. The revised selection rule explicitly includes separately recorded runtime/cleanup errors in its technical-failure tie-breaker.
