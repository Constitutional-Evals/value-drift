# Full-parameter OCT pilot method

The experiment loads the official [Qwen/Qwen3.5-9B checkpoint](https://huggingface.co/Qwen/Qwen3.5-9B) and carries its updated weights through each DPO stage, introspective SFT stage, and subsequent review. This is a budget-oriented adaptation of [Open Character Training](https://arxiv.org/html/2511.01689v1), with implementation checked against the local original repository, particularly `finetuning/distillation/qwen.sh`, `finetuning/introspection/qwen.sh`, and `character/introspection/`.

## Verified model interface

The official [configuration](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/config.json) names `Qwen3_5ForConditionalGeneration`, `model_type=qwen3_5`. The language backbone is dense, not a mixture of experts: 32 layers, hidden width 4096, intermediate width 12288, and a repeating three Gated DeltaNet layers followed by one gated full-attention layer. Full attention has 16 query heads, four KV heads, and dimension 256. DeltaNet has 16 key heads and 32 value heads of dimension 128. The vocabulary is 248,320. Input/output embeddings are untied. The released model also contains a 27-layer vision encoder, so total checkpoint parameters exceed the nominal 9B language count. The checkpoint index also contains 15 `mtp.*` auxiliary speculative-prediction tensors. The ordinary official `Qwen3_5ForConditionalGeneration` class does not instantiate this auxiliary head; the standard loader ignores those tensors. We use that ordinary supported architecture, do not enable speculative decoding, and do not claim to optimize the omitted auxiliary MTP tensors. The instantiated architecture has 9,409,813,744 parameters: 8,953,803,264 text and 456,010,480 vision (counted without allocation on the meta device with Transformers 5.17.0).

We use the official Transformers class with `trust_remote_code=False`, SDPA attention, `AutoTokenizer`, and string-only chat messages. The [official Transformers source](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py) implements the text path through the multimodal backbone and its language head. All model parameters have `requires_grad=True`; text-only input leaves vision parameters outside the computation graph. Those parameters are retained in full checkpoints but naturally receive no gradients or optimizer states. This is not backbone freezing or an adapter approach. The first training step records every parameter without a gradient and fails if an active text parameter is missing one.

The [checkpoint chat template](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/chat_template.jinja) defaults to thinking, and accepts `enable_thinking=False` to insert an empty thinking prefix. Qwen3-style `/think` or `/nothink` text commands are not supported controls. Review thinking is an explicit caller setting; ordinary generation, introspection, and evaluation default to non-thinking. The checkpoint text configuration declares end-of-text token 248044, while its chat tokenizer uses end-of-message token 248046 as EOS, and there is no separate generation configuration file. We explicitly stop on the union of both IDs, removing the terminal token from decoded response text. This corrects an engineering-smoke discovery where relying on the model configuration alone leaked a literal end-of-message marker. Transformers 5.17 returns a `BatchEncoding` mapping from tokenized chat templates by default; we explicitly request plain token IDs and normalize mapping/tensor results at the training boundary. Raw generated text, output length, thinking setting, and stop-versus-length reason are saved. The review runner must reject length-limited output before executing any purported final submission.

Native tool calls use `<tool_call><function=NAME><parameter=NAME>VALUE</parameter></function></tool_call>` markup, with multiline string parameter values. Tools are supplied to the official chat template. The parser excludes completed thinking content and rejects missing, incomplete, duplicate-argument, or structurally malformed calls. Tool results are returned through the template's `tool` message role.

## Distillation and introspection

The main trajectory uses revision-pinned Qwen/Qwen3.5-27B as a fixed teacher, conditioned on the complete submitted constitution. This stronger open-weight teacher fits sequentially on the same H200; its weights never evolve. The engineering smoke initially used frozen M0. Teacher choice, throughput and quality limitations are recorded in `agents/notes/01_pilot/TEACHER_REVIEW.md`. The evolving student answers the same fixed user prompts without a constitution. Separate, resumable teacher and student generation files allow the teacher to be unloaded before loading the student. Empty and identical responses are excluded, and length-limited responses are excluded by default; retained and excluded counts are saved. Chosen means the assigned recipe target, not a independently verified quality preference. Small-sample qualitative inspection remains necessary.

Each DPO pair contains a plain user prompt and the teacher/student answers. The constitution-bearing teacher system message is absent from policy and reference inputs. The exact same formatted token arrays are evaluated under the current pre-update checkpoint immediately before training; their summed response log probabilities and token arrays are saved. The reference is never simultaneously resident with another model and is recomputed for each round. There is no reuse of M0 reference probabilities in later rounds.

The objective is `-logsigmoid(beta * ((logp_chosen-logp_rejected) - (ref_chosen-ref_rejected))) + nll_coef * (-logp_chosen / chosen_tokens)`, with beta 0.1 and chosen NLL coefficient 0.1. These components follow OCT. We omit OCT's additional tokenwise KL penalty (its Qwen shell config uses coefficient 0.001); standard reference-relative DPO is retained. This simplification avoids storing a full reference vocabulary distribution or keeping a second model resident.

Post-DPO weights generate both introspection components, conditioned on the submitted constitution. Reflection uses a fixed bank of 10 neutral templates applied to the fixed training situations (`prompts/introspection.jsonl`), focusing on judgment, uncertainty, competing considerations, and correction. This replaces OCT's biography/diary/backstory prompts and repeated samples with more varied situated reflection without inviting invented personal histories. No held-out evaluation or editing transcript enters this bank.

Self-interaction alternates the speaking role between identical post-DPO instances, represented by role-swapped histories in one model session. Half the sessions invite free topic choice and half invite reflection on character and difficult choices. Raw turns are saved individually. Four generated turns are the provisional pilot default, shorter than OCT's ten. The SFT dataset retains assistant turns with their actual preceding context, strips constitution conditioning, and uses a neutral self-interaction system message for dialogue. Every assistant target is trained once; preceding turns are masked. Reflection and interaction counts are configured and must be frozen after the engineering benchmark, before a scientific trajectory begins.

## Optimization, memory, and checkpoints

Both stages update full model parameters directly. There are no LoRA modules, quantized model weights, adapters, selectively frozen text layers, or adapter merges. Optimizer states are reset between stages and rounds; model weights are never reset. We use FP32 trainable weights and gradients with BF16 autocast, and bitsandbytes AdamW8bit moments. FP32 parameter storage preserves updates that could disappear when written directly into BF16 weights. Inference loads the saved checkpoint into BF16; this rounds parameters for computation, as BF16 autocast also does for matrix operations, while the saved FP32 checkpoint remains the source for subsequent training.

For approximately 9–10B total parameters, FP32 weights cost roughly 36–40 GB, active FP32 gradients roughly 36 GB, and two 8-bit moments roughly 18 GB plus quantization metadata. Inactive vision weights occupy storage but have neither gradients nor moments. For the exact instantiated architecture, weights occupy 37.639 GB, text gradients 35.815 GB, and 8-bit moments 17.908 GB: 91.362 GB total before optimizer quantization metadata, activations, temporary buffers, and allocator overhead. The actual provisioned H200 reports 150.110 GB through `torch.cuda` (about 139.80 GiB), and `nvidia-smi` reports 143,771 MiB; memory planning uses these measured values rather than the advertised 141 GB label. Ordinary FP32 AdamW moments would add approximately 72 GB instead of 18 GB and would leave insufficient practical room on one H200; AdamW8bit is a full-parameter optimizer adaptation, not parameter-efficient fine-tuning. CPU optimizer offload is a possible fallback if the measured configuration fails, but is not currently implemented and must not be claimed as active.

Gradient checkpointing, microbatch one, and accumulation reduce activation pressure. The frozen main DPO sequence limit is 2560; SFT is 3072 to accommodate short interaction history. The loss applies the official language head in token chunks and checkpoints each projection/cross-entropy calculation, avoiding a full sequence-by-248320 FP32 logits tensor. Main training rejects any target truncation before reference scoring or optimization. Engineering length-stress fixtures explicitly permit counted truncation and never enter the scientific trajectory; a truncated target never receives an artificial EOS. Prompts too long to leave a meaningful target cause an explicit error rather than silent context removal.

Actual memory and throughput must come from the H200 smoke. `configs/training-smoke.json` is an engineering configuration for two short preference pairs and two short SFT examples, with explicit smaller lengths. It is not a scientific trajectory. Engineering smoke used batched Transformers. The frozen main trajectory uses isolated vLLM for review, teacher/student responses, introspection and evaluation; full-parameter optimization stays in Transformers. Optional compatible FLA and causal-conv1d kernels can improve DeltaNet speed; installed versions and successful forward/backward compatibility must be recorded, without assuming a serving engine supports this model correctly.

Each completed stage writes a usable full checkpoint, tokenizer, losses, input checkpoint location, full-parameter gradient report, peak CUDA allocation, and elapsed time. A completion marker is written after saving. Partial failed stages are not considered completed. Reference and generated data files remain inspectable across failures; the lead may remove a large intermediate DPO checkpoint only after the final SFT checkpoint has been verified and its provenance recorded. No checkpoints are published.


## CUDA extension build record

The first optional causal-conv1d 1.7.0 build failed because the Python-packaged CUDA compiler lacked `nv/target`, a CCCL header. The matching CUDA 13.0 installation is `nvidia-cuda-nvcc==13.0.88`, `nvidia-cuda-crt==13.0.88`, `nvidia-nvvm==13.0.88`, and `nvidia-cuda-cccl==13.0.85`; `ninja==1.13.2` supplies the parallel build runner. Installing CCCL supplied the missing header without changing model code or running another GPU workload.

The official causal-conv1d 1.7.0 setup file hardcodes several CUDA architectures rather than honoring `TORCH_CUDA_ARCH_LIST`. For this H200, its source distribution was extracted under `/workspace/build/causalconv-sm90/causal_conv1d-1.7.0`, and a single local build-scope override assigns `cc_flag = ["-gencode", "arch=compute_90,code=sm_90"]` after the original architecture selection. Numerical kernel source was unchanged. The build uses `CUDA_HOME=/workspace/venv/lib/python3.12/site-packages/nvidia/cu13`, `MAX_JOBS=4`, `CAUSAL_CONV1D_FORCE_BUILD=TRUE`, and pip `--no-build-isolation --no-deps`; source URL and patch description are recorded in `/workspace/build/causalconv-sm90/build-source.json`. Build output is saved in `runs/causalconv-install-3.log`. Runtime forward/backward validation remains required before using the extension in a scientific trajectory.


Compilation produced all SM90 objects, then linking failed because the Python-packaged runtime had `libcudart.so.13` but no unversioned linker name. Adding `libcudart.so -> libcudart.so.13` inside the same CUDA `lib` directory allowed the already compiled objects to link; the objects were reused rather than recompiled. This step is recorded in `runs/causalconv-link-fix.log`, followed by packaging in `runs/causalconv-install-4.log`. The first build used distutils because the separately installed ninja executable was outside the SSH subprocess PATH.

The resulting causal-conv1d 1.7.0 extension installed successfully and passed a CPU-only import check with Torch 2.14.0+cu130; `torch.cuda.is_initialized()` remained false. `runs/causalconv-import.json` records this check. GPU numerical and throughput validation is a separate lead-controlled step.

## Optional isolated vLLM inference backend

An optional inference backend was prepared before the scientific trajectory: **vLLM 0.29.0**, **PyTorch 2.13.0**, and **Transformers 5.17.0**, installed in the separate Python 3.12 environment `/workspace/venv-vllm`. The training environment `/workspace/venv` remains separate. The release's default PyPI build uses CUDA 13.0; its tagged dependency/source definitions and release notes were checked rather than relying on older installation-page CUDA wording. On this pod the older `uv` rejected `--torch-backend=cu130`, so the successful installation used the release's default PyPI packages:

```bash
uv venv --python /usr/bin/python3 /workspace/venv-vllm
uv pip install --python /workspace/venv-vllm/bin/python 'vllm==0.29.0'
```

[`vllm_session.py`](../../recursive_oct/vllm_session.py) launches one separate interpreter/process group per model session. JSON requests use an inherited Unix socket; stdout/stderr go to `runs/inference_logs/`. The engine persists across batches within that session. Closing the session terminates its owned process group before full-parameter training loads. The worker inherits `HF_HOME`; the pod's existing model cache is `/workspace/huggingface`. No alternate or quantized checkpoint is substituted. Full FP32 training saves are loaded with explicit BF16 inference dtype, as with the Transformers inference path. `language_model_only=True` avoids loading the unused vision tower for these text-only inputs; it does not modify saved training weights.

The worker renders the checkpoint's own chat template with explicit `enable_thinking` and tool schemas, requests `return_dict=False`, and normalizes the result to flat integer token IDs before handing it to vLLM. It checks input and total-context limits without truncation. Both the model's EOS and chat `<|im_end|>` terminate generation. Decoding removes terminal EOS while retaining thinking/tool markup; native `stop` and `length` finish reasons are preserved, and unexpected finishes fail explicitly. Initial engine settings use BF16 without quantization, tensor parallelism 1, CUDA graphs, a 32-sequence/capture limit, 32,768-token context, and disabled prefix caching. The final run configuration, not these provisional benchmark settings, determines the frozen backend.

Each request gets `generation_seed = base_seed + session_request_index`, with a monotonically increasing index across batches. This prevents identical self-interaction prompts from receiving identical seeded samples by construction. The seed is saved with every generation. Restarting a partially completed generation stage resets the worker's index for remaining requests, so resumed sampling is **not bitwise equivalent** to an uninterrupted run; already saved responses are reused. This limitation must be reported if a generation stage is resumed. Transformers and vLLM are also not expected to produce identical samples from the same nominal seed.

CPU validation passed seven adapter tests and actual tokenizer checks for both M0 and the saved full-parameter engineering checkpoint. Both installed tokenizers returned `BatchEncoding` by default, confirming the need for normalization. Explicit thinking-off/on synthetic tool prompts produced 413/411 tokens, respectively, and CUDA remained uninitialized during these checks. **These results do not establish GPU correctness, checkpoint loading, or throughput.** The lead must benchmark M0 and the saved full-parameter checkpoint, including a synthetic tool-call example and batches of ordinary prompts, before selecting and freezing this backend for a trajectory. Any later scientific backend change requires explicit separate labeling.

Primary implementation references: [vLLM 0.29.0 release](https://github.com/vllm-project/vllm/releases/tag/v0.29.0), [tagged Qwen3.5 implementation](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/model_executor/models/qwen3_5.py), and [tagged offline API](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/entrypoints/llm.py).

Measured H200 engineering stress subsequently validated DPO at exactly 2,048 tokens with two optimizer steps and two microbatches per step: peak allocation was 134.855 GB, including resident gradients and 8-bit optimizer moments. SFT at exactly 3,072 tokens passed at 107.741 GB in the mixed short/long benchmark. See `reports/methods/TRAINING_BENCHMARK.md` for configuration details and limits on extrapolation.


## Frozen full-001 protocol

The experimental M0 revision is `c202236235762e1c871ad0ccb60c8ee5ba337b9a`; fixed teacher and offline judge are Qwen/Qwen3.5-27B revision `fc05daec18b0a78c049392ed2e771dde82bdf654`. The same-family teacher/judge arrangement is a confound, and the judge's four valid smoke outputs establish JSON functionality only. Teacher targets can hallucinate, overrefuse, or mishandle uncertainty; they are assigned preferences, not gold labels. We do not hand-rewrite their answers.

All1500 fixed training prompts remain in the bank. Preference generations allow1536 outputtokens; held-out responses allow2048, and judging2048. Introspection generates512 situated reflections and64 four-turn conversations with768 tokens per turn; interaction guidance asks for100–200words per contribution. This makes short exchanges practical while preserving fixed templates across rounds. Truncated/empty/identical preference targets are excluded with counts; introspection filtering and behavioral missingness remain visible. Teacher generation uses the same explicit non-thinking sampling parameters as the student. Review alone uses thinking, up to8192 outputtokens.

The main configuration is `configs/full-001.json`, frozen before the first scientific review. Literal snapshots of12 protocol inputs are saved and checked on resume. Models do not see held-out prompts, scores, credentials, prior reviews, or infrastructure controls. Only full-information is executed. Every stage resets optimizer state while retaining the immediately preceding full weights. Five completed rounds is the administrative maximum.

Measured full-parameter DPO at2560 with two optimizer steps and two accumulated microbatches peaked at135.158GB of150.110GB available, including resident gradients and optimizer moments. SFT3072 peaked at107.741GB. Main accumulation8 has the same single-microbatch activation shape and resident-gradient condition; the run still records actual peaks. vLLM measured1,553 aggregate tokens/s on M0 batch32; the27B teacher sample measured341tokens/s at batch12. These are different workloads, not a controlled speed comparison. We conservatively allow about4hours per round including generation, reference scoring, training, model reloads and evaluation (~93USD for five rounds at4.635USD/h), plus preparation/retries and the storage/cleanup reserve.
