# Full-parameter OCT pilot method

The experiment loads the official [Qwen/Qwen3.5-9B checkpoint](https://huggingface.co/Qwen/Qwen3.5-9B) and carries its updated weights through each DPO stage, introspective SFT stage, and subsequent review. This is a budget-oriented adaptation of [Open Character Training](https://arxiv.org/html/2511.01689v1), with implementation checked against the local original repository, particularly `finetuning/distillation/qwen.sh`, `finetuning/introspection/qwen.sh`, and `character/introspection/`.

## Verified model interface

The official [configuration](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/config.json) names `Qwen3_5ForConditionalGeneration`, `model_type=qwen3_5`. The language backbone is dense, not a mixture of experts: 32 layers, hidden width 4096, intermediate width 12288, and a repeating three Gated DeltaNet layers followed by one gated full-attention layer. Full attention has 16 query heads, four KV heads, and dimension 256. DeltaNet has 16 key heads and 32 value heads of dimension 128. The vocabulary is 248,320. Input/output embeddings are untied. The released model also contains a 27-layer vision encoder, so total checkpoint parameters exceed the nominal 9B language count. The checkpoint index also contains 15 `mtp.*` auxiliary speculative-prediction tensors. The ordinary official `Qwen3_5ForConditionalGeneration` class does not instantiate this auxiliary head; the standard loader ignores those tensors. We use that ordinary supported architecture, do not enable speculative decoding, and do not claim to optimize the omitted auxiliary MTP tensors. The instantiated architecture has 9,409,813,744 parameters: 8,953,803,264 text and 456,010,480 vision (counted without allocation on the meta device with Transformers 5.17.0).

We use the official Transformers class with `trust_remote_code=False`, SDPA attention, `AutoTokenizer`, and string-only chat messages. The [official Transformers source](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py) implements the text path through the multimodal backbone and its language head. All model parameters have `requires_grad=True`; text-only input leaves vision parameters outside the computation graph. Those parameters are retained in full checkpoints but naturally receive no gradients or optimizer states. This is not backbone freezing or an adapter approach. The first training step records every parameter without a gradient and fails if an active text parameter is missing one.

The [checkpoint chat template](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/chat_template.jinja) defaults to thinking, and accepts `enable_thinking=False` to insert an empty thinking prefix. Qwen3-style `/think` or `/nothink` text commands are not supported controls. Review thinking is an explicit caller setting; ordinary generation, introspection, and evaluation default to non-thinking. The checkpoint text configuration declares end-of-text token 248044, while its chat tokenizer uses end-of-message token 248046 as EOS, and there is no separate generation configuration file. We explicitly stop on the union of both IDs, removing the terminal token from decoded response text. This corrects an engineering-smoke discovery where relying on the model configuration alone leaked a literal end-of-message marker. Transformers 5.17 returns a `BatchEncoding` mapping from tokenized chat templates by default; we explicitly request plain token IDs and normalize mapping/tensor results at the training boundary. Raw generated text, output length, thinking setting, and stop-versus-length reason are saved. The review runner must reject length-limited output before executing any purported final submission.

Native tool calls use `<tool_call><function=NAME><parameter=NAME>VALUE</parameter></function></tool_call>` markup, with multiline string parameter values. Tools are supplied to the official chat template. The parser excludes completed thinking content and rejects missing, incomplete, duplicate-argument, or structurally malformed calls. Tool results are returned through the template's `tool` message role.

## Distillation and introspection

The teacher is a frozen copy of the original checkpoint M0, conditioned on the complete submitted constitution. The evolving student answers the same fixed user prompts without a constitution. Separate, resumable teacher and student generation files allow the teacher to be unloaded before loading the student. Empty and identical responses are excluded, and length-limited responses are excluded by default; retained and excluded counts are saved. Chosen means the assigned recipe target, not a independently verified quality preference. Small-sample qualitative inspection remains necessary.

Each DPO pair contains a plain user prompt and the teacher/student answers. The constitution-bearing teacher system message is absent from policy and reference inputs. The exact same formatted token arrays are evaluated under the current pre-update checkpoint immediately before training; their summed response log probabilities and token arrays are saved. The reference is never simultaneously resident with another model and is recomputed for each round. There is no reuse of M0 reference probabilities in later rounds.

The objective is `-logsigmoid(beta * ((logp_chosen-logp_rejected) - (ref_chosen-ref_rejected))) + nll_coef * (-logp_chosen / chosen_tokens)`, with beta 0.1 and chosen NLL coefficient 0.1. These components follow OCT. We omit OCT's additional tokenwise KL penalty (its Qwen shell config uses coefficient 0.001); standard reference-relative DPO is retained. This simplification avoids storing a full reference vocabulary distribution or keeping a second model resident.

Post-DPO weights generate both introspection components, conditioned on the submitted constitution. Reflection uses a fixed bank of 10 neutral templates applied to the fixed training situations (`prompts/introspection.jsonl`), focusing on judgment, uncertainty, competing considerations, and correction. This replaces OCT's biography/diary/backstory prompts and repeated samples with more varied situated reflection without inviting invented personal histories. No held-out evaluation or editing transcript enters this bank.

Self-interaction alternates the speaking role between identical post-DPO instances, represented by role-swapped histories in one model session. Half the sessions invite free topic choice and half invite reflection on character and difficult choices. Raw turns are saved individually. Four generated turns are the provisional pilot default, shorter than OCT's ten. The SFT dataset retains assistant turns with their actual preceding context, strips constitution conditioning, and uses a neutral self-interaction system message for dialogue. Every assistant target is trained once; preceding turns are masked. Reflection and interaction counts are configured and must be frozen after the engineering benchmark, before a scientific trajectory begins.

## Optimization, memory, and checkpoints

Both stages update full model parameters directly. There are no LoRA modules, quantized model weights, adapters, selectively frozen text layers, or adapter merges. Optimizer states are reset between stages and rounds; model weights are never reset. We use FP32 trainable weights and gradients with BF16 autocast, and bitsandbytes AdamW8bit moments. FP32 parameter storage preserves updates that could disappear when written directly into BF16 weights. Inference loads the saved checkpoint into BF16; this rounds parameters for computation, as BF16 autocast also does for matrix operations, while the saved FP32 checkpoint remains the source for subsequent training.

For approximately 9–10B total parameters, FP32 weights cost roughly 36–40 GB, active FP32 gradients roughly 36 GB, and two 8-bit moments roughly 18 GB plus quantization metadata. Inactive vision weights occupy storage but have neither gradients nor moments. For the exact instantiated architecture, weights occupy 37.639 GB, text gradients 35.815 GB, and 8-bit moments 17.908 GB: 91.362 GB total before optimizer quantization metadata, activations, temporary buffers, and allocator overhead. The actual provisioned H200 reports 150.110 GB through `torch.cuda` (about 139.80 GiB), and `nvidia-smi` reports 143,771 MiB; memory planning uses these measured values rather than the advertised 141 GB label. Ordinary FP32 AdamW moments would add approximately 72 GB instead of 18 GB and would leave insufficient practical room on one H200; AdamW8bit is a full-parameter optimizer adaptation, not parameter-efficient fine-tuning. CPU optimizer offload is a possible fallback if the measured configuration fails, but is not currently implemented and must not be claimed as active.

Gradient checkpointing, microbatch one, and accumulation reduce activation pressure. The default DPO sequence limit is 1024; SFT is 3072 to accommodate short interaction history. The loss applies the official language head in token chunks and checkpoints each projection/cross-entropy calculation, avoiding a full sequence-by-248320 FP32 logits tensor. Large response truncations during training are counted; a truncated target never receives an artificial EOS. Prompts too long to leave a meaningful target cause an explicit error rather than silent context removal.

Actual memory and throughput must come from the H200 smoke. `configs/training-smoke.json` is an engineering configuration for two short preference pairs and two short SFT examples, with explicit smaller lengths. It is not a scientific trajectory. The generation backend is plain batched Transformers. Optional compatible FLA and causal-conv1d kernels can improve DeltaNet speed; installed versions and successful forward/backward compatibility must be recorded, without assuming a serving engine supports this model correctly.

Each completed stage writes a usable full checkpoint, tokenizer, losses, input checkpoint location, full-parameter gradient report, peak CUDA allocation, and elapsed time. A completion marker is written after saving. Partial failed stages are not considered completed. Reference and generated data files remain inspectable across failures; the lead may remove a large intermediate DPO checkpoint only after the final SFT checkpoint has been verified and its provenance recorded. No checkpoints are published.
